| --- | --- |
| 桌面切换通知 | `NSWorkspaceActiveSpaceDidChangeNotification` 是公开 API，但**程序化切桌面时根本不触发**（对照实验排除了环境因素：同一进程能正常收到 `didActivateApplication`）→ 事件源只能用轮询。⚠️ **实验 18（2026-10-04）说得更准了**：**真人用手势**切换时，实测**会触发**（5/5 次，而且比 50 ms 轮询早 2–30 ms）→ `SpaceObserver` 的通知快速通道确实有用，手势切换的跟随延迟 ≈0；程序化切换还是靠轮询 |
| 枚举桌面 | `dlopen` SkyLight 成功，`CGSCopyManagedDisplaySpaces` / `CGSGetActiveSpace` / `CGSMainConnectionID` 都能用 |
| 空间字典字段 | 键是 **`uuid`** / `ManagedSpaceID` / `id64` / `type` / `WindowManagerInfo`（**不是** `ManagedSpaceUUID`）；display 字典里还有 `Current Space`，可以直接拿到当前空间。**没有名称字段** → App 里给桌面起的名字只能存在本地 |
| **displayUUID → `NSScreen` 映射** | ✅ **实测一致**（2026-09-18）：`CGDisplayCreateUUIDFromDisplayID(NSScreen.deviceDescription["NSScreenNumber"])` = `AB24BB32-C5EC-D10A-6F9D-F01F35552F60`，和 SkyLight 的 `Display Identifier` 逐字符相同 → toast 能放到正确的显示器上。探测脚本是 `scripts/spike-probe.swift`（已经加了 `screens` 段，文本和 `--json` 两种输出都有） |
| 屏幕几何 | 主屏 `frame` = (0,0,1920,1200)，`visibleFrame` = (0,53,1920,1147)（Dock 在底部，没开自动隐藏）。toast 用 `visibleFrame` 定位，自然就避开了菜单栏和 Dock |
| **toast 窗口几何** | 水平居中，顶边离可见区顶部 80 pt（没变）。**2026-09-19 起改成定高胶囊**：高 32，宽 = 文字宽 + 2×14，最小 76。⚠️ 旧实测值 `w=87 h=39` / `w=193 h=39` 是**改版前**的数（字号 15、内边距 20/10），**新几何还要上真机重测**（`scripts/check-toast-window.sh --watch`；它判的是 `height >= 30`，32 照样命中）。`layer=25`、`alpha=1.00` 没变 |
| **toast 外观（2026-09-19 改版）** | 从"固定黑底 0.78 + 白字"换成了**跟随系统外观的原生 HUD 胶囊**：`NSVisualEffectView`（`material = .popover`、`blendingMode = .behindWindow`、`state = .active`）+ 用 `maskImage` 裁圆角（**`NSVisualEffectView` 没有 `cornerRadius`**，那是 UIKit 的）+ 1 px 动态描边（亮色下黑 0.12，深色下白 0.16）+ 文字用 `labelColor`、14 pt semibold。仍然不要任何权限 |
| **没有屏幕录制权限，也能看到自己的视图长什么样** | 用 `NSView.bitmapImageRepForCachingDisplay` + `cacheDisplay(in:to:)` 抓**自己窗口**的内容，不需要任何权限（用 `screencapture` 拍整屏才需要）。`scripts/preview-toast.swift` 就是这样出亮、深两张预览图的。代价是：预览用 `.withinWindow` 模糊窗口里的假壁纸，真机用 `.behindWindow` 模糊屏幕内容 —— **材质色调、圆角、描边、字体一致，模糊出来的实际画面不一致**。⚠️ **2026-10-04 起，整套设置窗口也能这样验收**（`UISnapshotTests`，`MULTIDOCK_UI_SNAPSHOT=1`）：要抓 `contentView.superview`（主题框视图）才**带标题栏和工具栏**，只抓 contentView 拍不到窗口 chrome；`@Observable` 失效后，要等一个 RunLoop 拍子 body 才重算，不等就会拍到旧页面；`NSTemporaryDirectory()` 返回的是 `/var/folders/...`，不是 `/tmp` |
| **`orderOut` 之后，窗口还会在 CG 窗口列表里留一阵** | 窗口 `orderOut` 后，`kCGWindowIsOnscreen` 立刻变成 false，但那条记录**还会在列表里留好几秒**才真正消失。拿窗口元数据核对「消失」时刻时，**一定要滤掉 `onscreen == false`**，不然报出来的时长会偏晚 |
| **`CGWindowListCopyWindowInfo` 读元数据零权限** | 实测没有屏幕录制权限时，也能读到 `kCGWindowLayer` / `kCGWindowAlpha` / `kCGWindowBounds` / `kCGWindowIsOnscreen`（**读不到 `kCGWindowName`**，系统把它抹掉了）。所以窗口类的验收完全不需要权限 |
| 菜单栏图标（补充） | 菜单栏设成自动隐藏时，状态栏窗口在 `y=-24`、`onscreen=false`，大约 51×24 —— 和 toast（`y=80`、高 32、水平居中）一眼就能分开 |
| 主动切桌面 | `CGSManagedDisplaySetCurrentSpace(cid, displayUUID, spaceID)` **能用**，**实测 0–6 ms 生效（立即提交，没有动画）** |
| **启动台数据库能读（2026-10-06）** | 位置 = `$DARWIN_USER_DIR/com.apple.dock.launchpad/db/db`（`confstr(_CS_DARWIN_USER_DIR)`；本机是 `/var/folders/sw/…/0/`）。就是个**普通 SQLite 库**（WAL，`db` + `db-shm` + `db-wal`，`rw-r--r--`）→ 用 `SQLITE_OPEN_READONLY` 直接读，**不要权限，也不写任何东西**。真机实测：**27 个文件夹、160 个 App，bookmark 解析成功 160/160**（包括 `/System/Volumes/Preboot/…` 下的 cryptex 路径，文件都在）。表结构（15.8.1）：`items(rowid, uuid, flags, type, parent_id, ordering)`，`type 1`=根 / `2`=文件夹 / `3`=页 / `4`=App；`apps(item_id, title, bundleid, storeid, category_id, moddate, bookmark)`；`groups(item_id, category_id, title)`。顺序看每一层的 **`ordering`**（rowid 和屏幕上的顺序无关，必须递归排序）；`parent_id = 0` 是根，**层级里会夹着 `type 3` 的页**（一个文件夹可以有多页），App 不直接挂在文件夹下面。⚠️ `bookmark` blob 以 `book` 魔数开头，是标准的 CFURL bookmark，用 `URL(resolvingBookmarkData:options:[.withoutUI,.withoutMounting])` 就能直接解 |
| **macOS 26 起没有启动台** | 系统用「应用程序」替掉了它（这是用户规格的前提）。判断方法：`ProcessInfo.processInfo.operatingSystemVersion.majorVersion < 26`；26 及以上时，数据库路径和文件夹数据都不存在，本 App 的「启动台」页显示说明并禁用 |
| **切桌面没有动画，而且加不上**（2026-09-18 复核，`spikes.md` 实验 7） | 程序化切空间是**硬切**：3 轮实测 **6 / 0 / 0 ms**。想加"左右滑动"，四条路全走不通：① `SLSManagedDisplaySetIsAnimating` 是**粘滞状态位**（置位后 600 ms 内 **101/101** 次采样仍是 true，不会自己复位），**而且它的返回值是 void ABI 留在寄存器里的残值** —— 同一次运行调 8 次都是 `-785121165`，换一次运行就成了 `-2752379`，**不能当成功标志**；② 会话级开关 `SLSSetSessionSwitchCubeAnimation`（值 `cube`/`transition`/`none`/`""`，对应 `kSLSSessionSwitchTransitionType*`）**只有 set，没有 get**，偏好域里也找不到（`CGSessionCopyCurrentDictionary()` 只有 11 个键，全是审计、用户、登录态相关的），把 `__TEXT` 的 5,037,056 字节扫了一遍，只找到函数名本身 → **改了就还原不回去，违反无痕原则**；③ `SLSWillSwitchSpaces` 按 `(cid, CFArray)` 一试就 **SIGSEGV**（`array_call_as_integer_list`），签名不知道，**别再拿图形会话试错**；④ 合成按键事件被拦（`CGPreflightPostEventAccess()` 返回 true，但**阳性对照合成 `Cmd+Tab` 也没反应**）。真正的过渡动画在 WindowServer 内部的 `Transition{Slide,Cube,Flip,Blend,Shrink,Spiral,Drop,RadialBlur}Metal`，只给用户手势用。**⚠️ 2026-10-06 实验 28 修正了第④条**：合成按键被拦**不是权限问题** —— `AXIsProcessTrusted()` 和 `CGPreflightPostEventAccess()` 都是 true，`CGEventSource` 也创建成功，合成 ⌃→ 照样不切；**阳性对照 Cmd+Tab 同样没反应**，用 `swiftc` 编出独立二进制再测，结论一样；换 AppleScript 走，报 `-1743`。→ 事件是在**投递层**被系统拦下的，授权解决不了。产品上默认关掉合成这条路（配置项 `animatedDesktopSwitch`），设置界面里故意不露出来（假开关） |
| **怎么枚举私有框架的导出符号** | `nm` 在磁盘上找不到 SkyLight（框架在 dyld 共享缓存里，磁盘上没有实体文件）。得在**进程内**解析：用 `_dyld_get_image_header` 拿到镜像 → 遍历 `LC_SEGMENT_64`，取出 `__LINKEDIT`/`__TEXT` → **`LC_SYMTAB.symoff`/`stroff` 是共享缓存里的文件偏移**，要先借 `__LINKEDIT` 换算成 vmaddr 再取指针，直接当指针用会 SIGSEGV。脚本在 `scripts/spike-symbols.swift`，本机 SkyLight 一共 **23,474** 个导出符号 |
| ⚠️ Dock 热重载（**2026-10-03 实验 17 部分修正**） | notifyd 热重载**根本没有**：post `com.apple.dock.prefchanged`（darwin、分布式、**CoreDock MIG 版**三种都试过）一点用都没有。**但 MIG 通道本身是有的**：HIServices 的 `CoreDock*` 函数（由 ApplicationServices 重新导出，可以直接链接）→ Dock 的 launchd 端点 `com.apple.dock.server`，**没有权限闸门**。实测 `CoreDockSetTileSize`（参数按 **float 的位型**塞进 Int32 传，越界会被钳住）**不重启就能改域，还会持久化**；但 `SetPreferences(整域字典)` / `AddFileToDock(CFURL)` / `SendNotification` 都被 Dock **静默拒掉**（status=0，什么也不做）—— **条目热替换没打通，主路径还是 SIGHUP**。签名和完整矩阵见 `docs/spikes.md` 实验 17；探针在 `scripts/spike-coredock-probe.swift` |
| ✅ **`CoreDockSetAutoHideEnabled` typed setter 能用**（实验 20，2026-10-04） | `sendSetBooleanValue(id=3)` / `sendGetBooleanValue(3)`：第三方调用**立即生效，Dock 自己把它持久化到域里，PID 不变**（和 `SetTileSize` 是同一类；对照：对象类消息全被拒）。**用法叫"自动隐藏三明治"**：先 Set(true)，Dock 滑走 → SIGHUP（Dock 回来时是隐藏状态，所以重启看不见）→ 再 Set(false)，Dock 滑回来。已经在 `DockReloader` 里实现（参数 `sandwichRevealAutoHideTo:`），实现和降级语义见 `docs/spikes.md` 实验 20。⚠️ 15.8.1 的 CGWindowList **看不到 Dock 的容器窗口**（owner=Dock 一条都没有），"窗口离屏"不能当观测量，改用 Get 或域里的值 |
| Dock 重启 | `kill -HUP`：进程在 +13 ms 消失，+101 ms 回来（**总共约 101 ms 用不了**）。`kill -TERM`：Dock 先花约 255 ms 清理，总共**约 367–395 ms** 用不了。**主路径选 SIGHUP** |
| **launchd 的重启节流**（P3 实测，`spikes.md` 实验 5） | 离上一次重启**不到约 1 秒**就再重启，Dock 要**约 1070 ms** 才回来；间隔 **≥ 1 秒**只要**约 70 ms**。阈值在 0.6–1.0 s 之间。⚠️ **这不是"隐式节流"** —— `com.apple.Dock.plist` 里**本来就写着 `ThrottleInterval = 1`**（`launchctl print gui/501/com.apple.Dock.agent` 显示 `minimum runtime = 1`）。→ `DockReloader.minimumSpacing` 默认 1 s：先等够再重启（等的时候 Dock 照常能用），实测 Dock 用不了的时间是 **45–90 ms** |
| ⚠️ **别被"uptime 门槛"骗了 —— 这个假说已经被实测推翻**（2026-09-20，`spikes.md` 实验 11→12） | 真机日志里，uptime 6.5 s 和 1 s 的两次重启花了 **26 046 / 31 039 ms**，而 uptime ≥ 30 s 的 4 次只要 50–126 ms，看上去就像"launchd 有 ~10 s 的 crash-uptime 门槛"。**但控制实验直接否掉了它**：uptime 6.0 / 12.0 / 20.0 s 各测一次，再加 60 s 和 81 486 s 两个对照，**回来只用了 37–68 ms，一次都没被罚**。`com.apple.Dock.plist` 里本来写的就是 `ThrottleInterval = 1`（`launchctl print gui/501/com.apple.Dock.agent` 显示 `minimum runtime = 1`）。→ **`minimumSpacing` 别动**。26–31 s 是偶发的，根因还没定，见 §6.3 A8 |
| **判断节流窗口要看 Dock 进程的年龄，不看我们记得什么**（P4 实测修正） | 节流是**按服务**算的，跟我们记不记得自己重启过没关系。P4 验收时，上一条用例刚重启完 Dock，紧接着新建的 `DockReloader`（`lastRestartAt` 为 nil）马上又重启，被节流到 **1030 ms** —— 用户会看到 Dock 消失一秒多。→ 改成用 `proc_pidinfo(PROC_PIDTBSDINFO)` 读 `pbi_start_tvsec/tvusec` 算进程年龄（实测返回 **136 字节 = 结构体大小**，读得到）。改完后 P3 第一轮从 **1030 ms → 45 ms**。拿不到年龄时，才退回用内存里的记录 |
| **`kill -9` 掉 Dock 后多久恢复** | ⚠️ **不是固定值，要看 Dock 当时活了多久**。2026-09-18 第一次实测 **1072 ms**（当时 Dock 刚被重启过，吃了一次隐式节流）；2026-09-20 真机验收又测了一次，只要 **56 ms**（`69452 → 69457`，当时 Dock 已经活了约 1 秒，节流窗口已经过了）。→ **判据写成"3 秒内必须出现新的正数 PID"**，别拿某个具体毫秒数写断言。`DockPresenceMonitor` 负责兜底：**连续 8 轮看不到才动手**（默认 500 ms 一轮 = 4 秒），之后每 60 轮（30 秒）才再试一次 `kickstart`（一直催只会让 launchd 退避得更久） |
| **`NSRunningApplication` 会返回 `processIdentifier == -1`** | Dock 重启的那段时间里，`runningApplications(withBundleIdentifier: "com.apple.dock")` 会返回一个**正在退出**的实例，PID 是 **-1**（实测能复现）。`kill(-1, sig)` = 发给**当前用户的所有进程**，`kill(0, sig)` = 发给整个进程组。**一定要过滤出 `> 0` 的，发信号前再用 `proc_name` 确认进程名是 `Dock`** |
| **查 Dock PID 要花多久** | `NSRunningApplication` **0.6–1.4 ms**；`/usr/bin/pgrep -x Dock` **109–112 ms**（要起子进程，绝不能放进轮询热路径）；`proc_listpids(PROC_ALL_PIDS)` + `proc_name` **0.02 ms** |
| Dock 进程守护 | `/System/Library/LaunchAgents/com.apple.Dock.plist` 里是 `KeepAlive = {AfterInitialDemand:1, SuccessfulExit:0}` → 只有被信号杀死才会被拉起来；**正常退出（exit 0）不会重启，用户当场就没了 Dock** |
| **Dock 是否应用了写入** | 判据：我们写进去的 tile 不带 `GUID`，Dock 真读进去并应用后，会**补上 `GUID`**。正反两种情况都实测过。**回写是异步的**：P2 验收里 apply 一返回就读，还是 `nil`；轮询 200 ms 内就出现了 → 判据要配轮询，别读一次就断言。⚠️ **15.8.1 起不灵了（实验 19，2026-10-04）**：Dock 重启后 mod-count 照样 +1（说明重启后重读了），但 **persistent-apps 一点没改写，也不再回填 GUID**。15.8+ 的判据降为「条目跨 Dock 重启仍在 + mod-count 变化」，验收用例已经按系统版本分了条件 |
| **只写白名单键：实测成立** | P2 验收（2026-09-18）：apply 一次（改 `tilesize` + `magnification`，再加一个 Calculator 条目），跟操作前的全量域做 diff，**只有 `magnification` / `persistent-apps` / `tilesize` 变了**，白名单外的键一个都没动 |
| **别的进程写的 Dock 偏好，本进程马上就能读到** | 2026-09-18 实测：`/usr/bin/defaults write com.apple.dock tilesize -float 72` 之后，`CFPreferencesCopyMultiple` 马上读到 72.0（不用轮询，也不用等 Dock 重启）。有了这一条，「用户手拖图标」这件事**就能用脚本复现** —— `DockWatcher` 的判据是"可比指纹变了、且不等于我们写下去的那份"，而用户拖图标本来就是 Dock 进程在写同一个域，两种来源在偏好域这一层**分不出来，也不用分**。所以 `DockAcceptanceTests.testExternalDockChangeIsCapturedBackToActiveDesktop` 用 `defaults write` 加一次真实的 `DockReloader().reload()`，就等于一次真人拖动，A4 从"只能手测"变成了自动化回归 |
| **写外观键真的生效** | `tilesize` 36 → 52、`magnification` 翻转，写完域里就是新值，Dock 也重启了（PID 变了）。`persistent-apps` 的新条目补上了 `GUID`（实测 `i:1414651200` 之类，每次都不一样）→ Dock 确实按新偏好重建了 |
| **本机白名单键能不能用（逐键实测）** | **能用**：`persistent-apps` `persistent-others` `orientation` `tilesize` `magnification` `largesize` `autohide` `mineffect` `minimize-to-application`。**不存在**：`show-process-indicators`（域里没有）。`autohide-delay` / `autohide-time-modifier` 域里也没有，`DockAppearance.read` 读出来是 nil → 根本不会进写入集合。结论：**只写"域里已有的键"，这条规则就够了**，不用另设黑名单 |
